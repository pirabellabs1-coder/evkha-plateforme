Comment utiliser ce document

Ce playbook sert autant aux humains qu'aux agents IA (Claude & Codex). Il impose un protocole strict pour éliminer les hallucinations et la perte de contexte : chaque agent travaille sur une unité bornée, contractualisée et vérifiable.

Protocole obligatoire avant toute tâche

  1. Lire : ce plan (§01, §04, §08) + la fiche du module ciblé (§07) + la section du cahier des charges qu'elle référence.
  2. Contrat d'abord : produire/valider l'interface du module (modèles, schémas API, types, signatures) avant toute logique. Le contrat est la source de vérité ; aucun champ inventé.
  3. Périmètre borné : une branche = un module ou une tranche. Ne jamais déborder sur un module appartenant à l'autre agent (voir matrice §05).
  4. Traçabilité : chaque décision non triviale cite sa source (cahier, note Tobias, consignes d'écriture). Si l'info manque → marquer // TODO(décision) et lister dans §11, ne jamais inventer.
  5. Vérifier avant de livrer : passer la Definition of Done du module (§07) + les portes qualité globales (§08). Une tâche n'est « réussie » que si elle franchit ces portes.
Règle anti-dérive Si une tâche dépasse son périmètre ou nécessite de modifier un contrat partagé, on s'arrête : on ouvre une décision (§11) et on synchronise les deux agents avant de continuer. Mieux vaut une PR bloquée qu'un merge incohérent.
01

Mission & règles d'or non négociables

Cinq contraintes structurent tout le système. Toute implémentation qui en viole une est refusée en revue, même si elle « marche ».

1 · Industrialisation invisible

Note Tobias §9–13 · Consignes §1
Le client final ne voit jamais le pipeline. Séparation stricte couche interne (prompts, QA, logs, balises) ↔ couche client (rendu propre). Bannir « Étape 1.1 », « Point de contrôle », « CONTEXTE À RÉINJECTER », phrases méta.

2 · Plafond de coût IA < 2 €

Note Tobias §3–4 — inquiétude n°1
Coût réel par dossier visé < 1–2 €. Impose contexte glissant, anti-répétition, et un moteur de suivi de coût (tokens + € par chapitre / dossier / job). Un dépassement de budget = échec de la génération, pas un détail.

3 · Cohérence analytique totale

Note Tobias §5–6
Aucun chiffre contradictoire entre chapitres : même taille de marché, même TCAC, mêmes hypothèses. Les données validées sont stockées et réinjectées. Pas d'extrapolation fantaisiste : vraies données ou mention explicite.

4 · Charte rédactionnelle EVKHA

Consignes d'écriture (6 blocs)
Ton mentor, lexique simplifié, encadrés mentor (◆ → ! ✓), fiche projet en ouverture, annexe brief avant les sources, section Sources unique, charte graphique (or #C9A227 / noir #1A1A1A, Calibri). Limites : EM 80p · EC 45p · STR 45p · BP 80p.
5 · Confidentialité (NDA signé) Aucun secret dans le repo (clés, mots de passe, données client) — uniquement .env non commité + .env.example. Stockage client temporaire et purgé. Logs sans prompts ni données sensibles. Le repo doit passer en privé avant tout push de code métier (voir §11).
Adaptation géographique auto La logique des chapitres s'adapte à la zone : projet en Côte d'Ivoire → « marché mondial + africain » puis « national + local », jamais « marché européen » par défaut. La zone est une variable de cadrage, pas un libellé figé.
02

Architecture cible

n8n orchestre (webhooks, emails, appels simples). Django est le cœur métier (jobs, prompts, chapitres, statuts). Celery exécute le long et le relançable. PostgreSQL est la source de vérité. Le rendu passe par Google Docs puis Gamma.

Flèches pleines = flux synchrone · flèches clay pointillées = appels génération / notifications. Dashboard : Django Admin en V1, puis TanStack Start + Better Auth (même PostgreSQL) juste après.

04

Méthodologie scaffolding & modulaire

On construit chaque module en 4 couches dans l'ordre. On ne passe à la couche suivante que si la précédente est verte. C'est ce qui rend le travail parallèle sûr et coupe les hallucinations à la racine : le contrat précède toujours le code.

Couche 1

Contrat

Modèles de données, schémas API (entrée/sortie), types, signatures de service. Aucune logique. Revue + merge avant tout développement parallèle.

migrationspydantic/serializersOpenAPI
Couche 2

Squelette + tests

Stubs qui respectent le contrat (retours factices déterministes) + tests qui décrivent le comportement attendu (rouges au départ). Les fixtures évitent d'appeler les vraies APIs.

pytestfixturesmocks Claude/Google/Gamma
Couche 3

Implémentation

Remplir la logique jusqu'à faire passer les tests. Périmètre strictement borné au module. Tout besoin externe passe par un contrat déjà mergé.

logique métierintégrations réelles
Couche 4

Vérification

Definition of Done module (§07) + portes qualité (§08). Démo reproductible. La tâche n'est « réussie » qu'ici.

DoDCI vertedémo
Anti-hallucination
  • Le contrat est la seule vérité ; aucun champ/endpoint inventé.
  • Données marché : jamais extrapolées. Source réelle citée ou FACT_MISSING + flag.
  • Toute décision non sourcée → TODO(décision) dans §11, pas d'improvisation.
  • Tests = filet : un comportement non testé est considéré inexistant.
Anti-perte de contexte
  • Tâches auto-portées : fiche module + contrat + section cahier suffisent.
  • Context Engine = résumé opérationnel, pas l'historique brut.
  • Coherence Engine = mémoire des faits validés réinjectée à chaque chapitre.
  • Un fichier docs/decisions/ADR-*.md trace chaque choix d'architecture.
05

Stratégie de branches — Codex × Claude en parallèle

Trunk-based avec branches courtes (1 module ou 1 tranche = 1 branche = 1 PR). Les contrats partagés sont mergés en premier (fondation commune) ; ensuite les modules indépendants avancent en parallèle sans se marcher dessus. Revue croisée : chaque agent relit les PR de l'autre.

Conventions

conventions de branches & commits
# branches
feat/<module>-<tranche>     # feat/generation-context-engine
fix/<module>-<sujet>
chore/<sujet>               # infra, CI, deps
contract/<module>           # couche 1 — mergée en priorité

# commits — conventional commits
feat(generation): add sliding context builder
fix(intake): handle Tally 2xx within 10s
# 1 PR = 1 module/tranche, <= ~400 lignes diff visées

Protocole d'intégration

  1. main protégée : pas de push direct ; PR obligatoire + 1 review de l'autre agent + CI verte.
  2. Contrats d'abord : aucune branche d'implémentation ne démarre tant que le contract/<module> dont elle dépend n'est pas mergé.
  3. Rebase fréquent sur main ; branches courtes (< 2 jours de travail) pour limiter les conflits.
  4. Frontières = pas de collision : un module n'est modifié que par son owner ; un besoin transverse passe par une décision (§11), jamais par un patch sauvage.
  5. Template de PR imposé : objectif, périmètre, contrat respecté, DoD cochée, comment tester, captures/coût mesuré.

07

Fiches modules & Definition of Done

Chaque fiche est le brief d'une branche. Un agent ne code que ce qui y est écrit. La DoD définit « réussi ». Exemples sur les modules critiques ; les autres suivent le même gabarit.

generation — cœur de génération

owner: Claude · review: Codex · dépend de : contracts/deliverables, contracts/intake, moteurs

Orchestre la génération d'un dossier : pour chaque chapitre → charge template + injecte contexte (Context Engine) + appelle Claude + sauvegarde + extrait sources + crée résumé opérationnel + met à jour statut. Reprise unitaire par chapitre, idempotence par job_id.

Definition of Done

  • Un chapitre échoué se relance seul sans rejouer les autres (testé).
  • Idempotence : un webhook/déclenchement dupliqué ne crée pas de doublon.
  • Coût mesuré et stocké par chapitre (Cost Engine) ; budget dossier respecté sur un échantillon réel.
  • Aucune incohérence chiffrée détectée par le Coherence Engine sur le dossier test.
  • Statuts complets (pending/running/done/failed) + erreurs lisibles.
  • Tests verts (unitaires + 1 e2e mické) ; couverture du chemin nominal + 3 chemins d'erreur (timeout, tokens, réponse incomplète).

intake

owner: Codex · review: Claude

Transforme les réponses Tally en variables propres (SECTEUR, PAYS, PROJET, ZONE, éléments à retenir, demandes spécifiques, concurrents) + déclenche la fiche sectorielle.

  • Webhook répond 2xx en <10s, génération déléguée à Celery.
  • Variables normalisées + validées (schéma).
  • Champs manquants → statut « incomplet » explicite, jamais de valeur inventée.

documents + Rendering

owner: Claude · review: Codex

Assemble le dossier final dans Google Docs selon l'ordre EVKHA + applique la couche client.

  • Ordre respecté : page de garde → sommaire → fiche projet → chapitres → annexe brief → Sources.
  • Zéro balise interne / « Étape » / bloc QA dans le rendu (test automatisé de pureté).
  • Section Sources unique, regroupée par thème.
  • Encadrés mentor insérés aux chapitres décisifs.

integrations

owner: Codex · review: Claude

Clients API isolés derrière des interfaces (Claude, Google Docs/Drive, Gamma, email, Systeme.io, Tally).

  • Chaque client mockable (tests sans réseau).
  • Retries + timeouts + erreurs typées.
  • Aucune clé en dur ; tout via env.
  • Gamma : poll asynchrone + export testé avec le compte Evkha.

n8n workflows (5)

owner: Codex · review: Claude

Commande Systeme.io · formulaire Tally · suivi génération · livraison · erreur critique.

  • Workflows exportés en JSON versionné dans le repo.
  • Idempotence + vérif signature/secret quand dispo.
  • Notif Evangeline sur erreur (job ID, livrable, chapitre, message).
08

Garde-fous & portes qualité (globales)

Ces portes s'appliquent à chaque PR, quel que soit l'agent. Une PR qui n'en franchit pas une seule n'est pas mergeable. La CI les automatise au maximum.

Porte
Critère « réussi »
Lint & types
ruff + mypy (Python) / eslint + tsc (front) sans erreur.
Tests
Suite verte ; nouveau code couvert ; chemins d'erreur testés ; pas de test ignoré sans justification.
Migrations
makemigrations --check propre ; migration réversible ; pas de perte de données.
Secrets
Scan secret (ex. gitleaks) vert ; .env absent du diff ; .env.example à jour.
Contrat respecté
Aucune divergence vs le contrat mergé ; pas de champ/endpoint hors spec.
Traçabilité cahier
PR cite les sections de référence ; décisions non sourcées listées en §11.
Budget coût IA
Sur tâche de génération : coût mesuré ≤ plafond ; pas de régression de tokens.
Pureté couche client
Test automatisé : zéro fuite de balise interne / vocabulaire pipeline dans le rendu.
Revue croisée
1 approbation de l'autre agent ; template PR rempli ; démo reproductible décrite.
Définition de « réussi » (résumé) Une implémentation est réussie = contrat respecté + tests verts + DoD module cochée + 9 portes franchies + démontrable. « Ça tourne sur ma machine » ne compte pas.
09

Moteurs transverses — spécifications clés

Context Engine

Construit le prompt par couches, sans jamais envoyer les chapitres bruts.

generation/context.py — contrat
def build_context(job, chapter) -> str:
  # 1 fixe : rôle EVKHA + règles + style
  # 2 projet : variables + fiche sectorielle
  # 3 cumulatif : résumé opérationnel (pas l'historique)
  # 4 chapitre : objectif + template du chapitre
  # 5 qualité : points à vérifier

Coherence Engine

Magasin de faits validés réinjectés ; refuse les contradictions.

  • Stocke : taille marché, TCAC observé/projeté, hypothèses centrales, devise.
  • À chaque chapitre : injecte les faits + vérifie qu'aucune nouvelle valeur ne contredit un fait figé.
  • Adaptation géo : dérive les zones d'analyse depuis ZONE/PAYS.

Cost Engine

Comptabilité tokens → € à chaque appel.

  • Enregistre tokens in/out + coût par appel, chapitre, dossier.
  • Garde-fou : stoppe/alerte si le dossier dépasse le plafond.
  • Expose un récap (Admin V1, dashboard V6).

Rendering Engine

Interne → client. Le seul module autorisé à produire du texte vu par le client.

  • Strip balises, « Étape », blocs QA, phrases méta.
  • Applique charte (titres, filets or, encadrés mentor ◆ → ! ✓).
  • Fusionne toutes les sources en une section finale unique.
